# OfferFlow 简历与面试表达材料

本文档面向简历撰写和面试沟通场景，所有表述以当前代码和 `docs/llm-eval.md`、`README.md`、`AGENTS.md` 描述的实际实现为准。不包含未实现能力的夸大描述，不使用营销化措辞。

## 1. 项目名称建议

- 中文：OfferFlow（本地优先的 AI 求职机会决策台）
- 英文/技术向：OfferFlow — Local-first AI-assisted Job Opportunity Decision Workbench

命名保持中性、技术向，不使用"智能体平台""AI 中台"等超出实际范围的词。

## 2. 简历 Bullet（两个版本，各 3 条）

两版描述的都是同一份代码和同一套实现，区别在于表达侧重点。选哪版取决于投递岗位的方向。

### 版本 A：稳健版（面向高级前端 / 全栈前端岗位）

1. 独立设计并实现 OfferFlow：基于 Vue3 + TypeScript + Naive UI 的前端，配合 Node.js + Fastify + SQLite(better-sqlite3) 本地后端，构建岗位台账、AI 分析、人工确认、跟进决策的完整业务链路。
2. 设计 8 态沟通状态机与人工确认闸门（`pending_review` / `confirmed` / `deferred` / `rejected`），配合纯函数 `deriveDecision` 根据事实状态派生跟进策略、下一步动作和止损建议，逻辑可单独测试、无副作用。
3. 落地 SQLite 文档存储模式（结构化列 + `data_json` 字段共存）与本地数据快照导出/导入/发布/拉取脚本（`scripts/db*.ts`），支撑跨机器数据同步与备份恢复，不依赖云端账号。

### 版本 B：AI 应用工程化版（面向 AI 应用工程师 / AI 应用开发岗位）

1. 设计并接入 DeepSeek LLM 分析链路：基于原生 `fetch()` 实现 OpenAI-compatible Chat Completions 调用（`server/llm/provider.ts`），支持同步分析和 SSE 流式分析两种路径，流式路径通过 `response.body.getReader()` 实现真实逐块解析和前端渐进渲染。
2. 设计 `OFFER_FLOW_JSON` 结构化输出协议：约束 LLM 同时返回人读 Markdown 报告和机器可解析的 JSON 数据块，配合标记提取 + 代码块兜底的双层提取逻辑和 `success/not_found/invalid_json/partial` 四态容错解析（`src/app/offerFlowJson.ts`），原始文本无条件先落盘，解析失败不丢数据。
3. 为 Prompt 与解析协议编写基于真实样本的 Eval 测试集（`eval/offer-flow-json/cases/001-010`，覆盖标准/缺字段/非法枚举/代码块兜底等场景），通过 `npm run eval:offerflow-json` 可重复验证协议稳定性，并设计 Human-in-the-loop 边界：AI 分析结果强制先进入待确认状态，不会自动触发状态变更或外部动作。

**推荐使用版本 B**，理由见第 3 节。

## 3. 推荐版本与理由

投递方向如果偏向"AI 应用工程化 / LLM 应用开发"，推荐使用版本 B，因为它更直接对应 JD 里的 Prompt Engineering、结构化输出、LLM API 集成、工程化容错这些考察点，且每一条都能现场打开代码验证。

如果投递方向是通用高级前端或全栈岗位，且面试官对 AI 相关经历兴趣不大，可以用版本 A，突出前端工程能力、状态机设计和本地数据工程，AI 部分作为背景信息补充说明即可，避免喧宾夺主。

两版可以在同一份简历里合并使用（3+2 条），具体取舍以投递岗位 JD 为准。

## 4. 90 秒项目讲法逐字稿

推荐标题：**"我怎么把 LLM 能力工程化地嵌进一个有状态、有边界的真实业务流程"**

> 我做了一个叫 OfferFlow 的项目，起因是自己求职时 JD、公司背调信息、沟通记录和分析判断都散落在不同地方，复盘很痛苦。所以我把它做成一个本地优先的求职机会决策台。核心链路是：录入 JD 和公司信息之后，后端调用 DeepSeek 做结构化分析，通过 SSE 流式返回，前端逐块渲染出内容；同时我设计了一个叫 OFFER_FLOW_JSON 的输出协议，要求模型既给一份人看的报告，也给一份机器可解析的结构化数据，原始文本无条件先落盘，即使解析失败也不会丢数据，这块我也写了一套基于真实样本的 Eval 测试来验证协议的稳定性。但我最想说的是这条链路的工程边界：AI 分析结果不会直接变成自动动作，而是先进入一个待确认状态，由我自己看过之后选择确认、暂缓或拒绝，只有确认过的机会才会进入沟通状态机，再用一个叫 deriveDecision 的纯函数根据当前的事实状态派生出跟进策略。这个项目想证明的是，我能把 LLM 能力工程化地嵌入一个有状态、有边界、可测试的真实业务流程里，而不是简单套一层 AI 壳子。

讲述节奏建议：因果开场（10 秒）→ 核心链路（30 秒）→ 协议与容错（20 秒）→ 人工确认边界（20 秒）→ 一句话总结（10 秒）。

## 5. Demo 演示脚本（6 步，含观察点）

| 步骤 | 演示动作 | 面试官应观察到什么 |
|---|---|---|
| 1. 录入 JD | 新建岗位，填公司/岗位/城市/薪资，粘贴 JD 文本 | 表单结构清晰，支持从零录入一条真实岗位记录 |
| 2. 触发 AI 分析 | 点击"AI 分析 JD"按钮 | 请求发出后立即进入分析中状态，不是静默等待 |
| 3. 观察 SSE 流式输出 | 分析结果逐块出现，打字机效果 | 内容是真实分块到达，不是整体一次性渲染；网络中断时已生成内容不会丢失 |
| 4. 查看结构化结果 | 分析完成后展示 Markdown 报告 + 结构化字段（匹配度、风险等级、建议） | 同一次分析同时产出人读内容和机器可解析字段，说明 Prompt 对输出格式做了强约束 |
| 5. 人工确认 | 点击确认/暂缓/拒绝任一操作 | AI 结果不会自动生效，必须人工介入才能进入下一状态，体现 Human-in-the-loop 边界 |
| 6. 查看跟进决策 | 修改沟通状态，观察决策面板变化 | 决策建议随事实状态实时变化，且是只读派生逻辑，不会自己写数据库 |

## 6. 面试追问诚实应答（8 题）

### Q1 为什么不用 LangGraph / CrewAI 这类 Agent 框架？

当前链路是单轮"输入 JD → LLM 分析 → 结构化解析 → 人工确认"，没有多步骤规划、工具调用链或多 Agent 协作的需求，引入这类框架只会增加复杂度而没有对应的业务收益。如果未来需要多步骤任务分解（比如自动跨多个信息源做背调再汇总分析），会是引入编排框架的合理时机，但当前阶段这个需求不存在。

### Q2 为什么不做 RAG / 向量数据库？

RAG 解决的是"从大量非结构化知识库里检索相关片段再回答"的问题。OfferFlow 的输入是用户自己录入的单条 JD 和公司信息，规模和场景都不需要检索增强，直接把结构化上下文放进 Prompt 就能覆盖。如果以后要做"基于历史所有分析记录做趋势总结"这类跨记录检索需求，才会是引入向量检索的合理场景。

### Q3 为什么不用独立 Python FastAPI sidecar 承载 LLM 调用？

现有 Node.js + Fastify 后端已经承担了数据存储和业务逻辑，LLM 调用本质上只是一次 HTTP 请求（Chat Completions 协议），用 `fetch()` 就能完成，没有必须依赖 Python 生态（比如特定的模型库、数据科学工具链）的场景。拆一个额外服务会增加部署和维护成本，但不会带来对应的能力提升。

### Q4 DeepSeek 和 OpenAI-compatible 接口是怎么理解的？

代码里的配置变量同时兼容 `OFFERFLOW_LLM_*` 和 `DEEPSEEK_*` 两套命名（`server/llm/provider.ts`），请求体格式是 Chat Completions 兼容格式（`messages`/`role`/`content`/`stream` 字段）。这是行业里"OpenAI-compatible"接口形态的通用叫法，不代表调用的是 OpenAI 官方服务——实际接入的模型服务商是 DeepSeek，走的是 DeepSeek 提供的 Chat Completions 兼容端点。

### Q5 AI 输出不稳定怎么处理？

原始文本无条件先落盘，不管后续解析成功与否都不会丢失。解析本身做了分层兜底：先按约定标记提取，找不到再退而查找代码块，字段命名或枚举值不对做归一化处理，最终返回 `success/not_found/invalid_json/partial` 四种状态而不是简单的成功/失败布尔值。这套逻辑用 `eval/offer-flow-json/cases/001-010` 这批真实构造的异常样本做了验证（`npm run eval:offerflow-json`，详见 `docs/llm-eval.md`）。

### Q6 SSE 具体优化了什么？

优化的是"首次看到内容"的等待体验：不流式的情况下用户要静默等待整段响应生成完才能看到任何内容，流式之后几秒钟就能看到内容开始逐块出现。这不是伪造的打字机动画，是真实按 SSE 协议逐块转发模型返回的内容（`server/routes/llm.ts` 的 `analyze-job-stream` 路由 + 前端 `response.body.getReader()` 逐块读取）。

### Q7 这个项目和普通 CRUD 后台有什么区别？

普通后台处理的信息本身是确定、干净的，主要工作是录入、查询、修改。这个项目多了一层"处理不确定信息"：LLM 输出格式可能不稳定，内容可能有偏差，所以需要做容错解析、设人工确认闸门、用 Eval 测试防止协议漂移。这套处理不确定性输出的思路是可以迁移到其他 AI 应用场景的通用能力，不是 OfferFlow 专属的一次性代码。

### Q8 一个前端工程师怎么算是做了"AI 应用工程化"？

这个项目里我做的不只是调用一个 LLM 接口展示结果，而是完整设计了：约束 LLM 输出格式的 Prompt 协议、应对输出不稳定的多层容错解析、验证协议稳定性的 Eval 测试集、划清"AI 该做什么、人该做什么"的产品边界（Human-in-the-loop）、以及把这套边界代码化的状态机和纯函数决策规则。这套组合体现的是"能把 AI 能力工程化地嵌入一个有状态、可测试、可复盘的真实业务流程"，而不是单纯的接口调用能力。

## 7. 30 秒极简版本

我做了一个本地优先的 AI 求职决策台，叫 OfferFlow。它把 JD 分析、机会评估和 Boss 沟通进度整理成结构化数据，用 DeepSeek 做分析，SSE 流式返回结果，但 AI 给的建议不会直接生效，必须经过人工确认才会进入后续状态流转。这个项目不是简单套一个 ChatGPT 壳子，而是我在设计 AI 输出协议、容错解析、状态机和决策规则这些工程细节，证明我能把 AI 能力真正落到业务闭环里，不只是写页面。

- [ ] 如果现场 LLM 调用失败，直接切换到提前准备好的截图或录屏结果继续讲，不要卡在这里重试

## 9. 现场 LLM 调用失败时的兜底策略

如果现场没有配置好 DeepSeek Key，或者网络/接口异常，系统会返回明确的"未配置"或错误提示，不会卡死或抛出看不懂的报错——可以直接演示这个提示，说明"配置缺失或调用失败时会有清晰提示，不会悄悄失败"，然后切换到提前准备好的分析结果截图或录屏继续讲解，不要在现场反复重试。手动粘贴外部 AI 结果的备用路径依然保留，也可以作为临时替代演示。

## 10. OCR 不是 Demo 重点

JD 截图粘贴和 OCR 识别只是录入体验的辅助手段，不是这个项目要证明的核心能力。如果现场识别效果不理想（中文小字号、低对比度场景下准确率会下降），直接手动打字输入 JD 文本即可，不需要在识别质量上纠结或反复重试。演示时间应该集中在 SSE 流式输出、结构化协议、人工确认和决策规则这几个更有工程含量的环节上。

## 11. 已知诚实边界（面试中如被问起，直接如实说明）

- 流式分析路径（`analyze-job-stream`）此前存在输入信息不完整的问题（未正确传入 `profile` 和 `companyInput`），已修复并通过 `resolveAnalyzeJobInput` 统一两条路径的输入构造逻辑，详见 `docs/llm-eval.md`。这是已经解决的历史问题，不是当前遗留风险。
- 不支持任意模型厂商切换，当前只接入 DeepSeek 一家，走 OpenAI-compatible 协议形态，理论上可扩展但未验证。
- 不做自动投递、不自动联系 HR、不做完整多轮 AI 对话——这是有意的产品边界，不是技术能力缺失。
