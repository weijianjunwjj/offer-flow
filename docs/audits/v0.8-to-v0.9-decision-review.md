## 1. 执行摘要

- **¥711.85 不是失控，但结构不健康**：工作量密度（100 commits / 47809 净行 / 37 API / 13 表 / 1506 测试 / 0 类型错误）对应的价格不算离谱，但 90.6% 的费用集中在 Opus 4.8，且相当一部分 Opus 用量花在"核验状态、复述交接文档"这类不需要 Opus 裁决能力的步骤上。问题不是"贵"，是"贵在不该贵的地方"。
- **v0.8 的核心矛盾是发布节奏，不是工程质量**：V8-2～V8-6 五个波次代码完成、测试通过、人工验收通过，但三个门禁（`radarEnabled`/`radarAnalysisEnabled`/`radarRecommendationsEnabled`）全部默认关闭，GA 当天用户能感知的新增能力只有 BOSS 采集桥。这是产品发布策略的选择（渐进开关），不是代码没写完，但这个选择**没有配套"何时开灯"的承诺**，导致高投入和零可见 ROI 同时成立，账无法平。
- **v0.9 的第一优先级不是新功能，是把 v0.8 已经建好的能力变成用户可用的能力**：先开 `radarEnabled`，跑通端到端真实使用反馈，再决定是否开 Analysis/Recommendation。在没有真实用户验证 Radar 之前新增任何 Radar 相关能力，都是在未验证的地基上继续加盖。

## 2. ¥711.85 成本是否合理

不给"贵/不贵"的单一结论。按审计给出的事实拆成四类，每类给权重和处理方式，不伪造无法拆分的具体金额。

### 2.1 必要产品复杂度（权重：中）

对应事实：13 张新表（v7 12 张 + v8 1 张）支撑 Candidate/Version/Action/Promotion 分层、37 条 API、5 个子域服务层拆分、schema v7→v8 迁移+生产受控升级+selftest+备份验证全链路。

- 是否保留：保留。这是"评审工作台 + AI 分析 + 推荐 + 正式晋升"四条业务链路能够独立按波次交付、互不冲突的前提，审计 1.8/1.9 节确认没有出现整体推翻重做。
- v0.9 处理：不再新增同等量级的领域模型工作，转入使用和验证阶段（见任务 4）。

### 2.2 必要质量与可靠性投入（权重：中高）

对应事实：测试 churn 17442 行与代码 churn 21200 行同量级；79 个新 spec 文件；1506 用例、4 个失败复测 46/46 通过（并发资源争用，非回归）；`vue-tsc` 0 错误；DeepSeek JSON 截断问题最终根治并沉淀到 memory。

- 是否保留：保留。审计明确"测试是随功能同步添加，不是先冲代码后补"，且 v0.8 涉及生产数据库结构变更和 AI 结构化输出，可靠性投入的必要性高于一般功能开发。
- v0.9 处理：vitest 全局超时/并发度需要调整（审计已指出 5000ms 偏紧），这是唯一一项"投入本身合理但配置需要优化"的条目，成本很低，直接改。

### 2.3 可以优化的流程开销（权重：高）

对应事实：40 个会话中 12 个（30%）是"接管/交接"性质，核心动作是"读文档→复述理解→核对 git 状态"；审计 3.8 节明确这类任务"理论上 Sonnet 5 即可完成大部分核验步骤"；Opus 平均单条消息 token 消耗显著高于 Sonnet，且 Opus 调用量本身是 Sonnet 的 8 倍（量价双重叠加）。

- 是否保留：不保留现状。这是本次审计里唯一一类"事实证据充分、方向明确、可执行"的浪费来源——不是任务本身不该做（交接确实需要核验状态），而是**默认模型档位选错了**。
- v0.9 处理：交接/接管类会话默认起手用 Sonnet，只有在核验中发现需要裁决生产风险或架构歧义时才升级 Opus（具体规则见任务 5）。

### 2.4 可以避免的浪费（权重：低）

对应事实：`analysis-e2e/gatedProvider.ts` 创建后被替换（规模小，不在 churn 前 20）；DeepSeek JSON 截断第一版"处理非法响应"（`0c55d29`）在根因修复（`60dbbbd`）之前提交，属于一次诊断返工但当天闭环。

- 是否保留：这两项本身规模小，审计已明确"不构成显著返工成本"，没有必要为了显得完整而夸大成本占比。
- v0.9 处理：DeepSeek 截断的经验已写入 memory（`deepseek-flash-reasoning-budget`），意味着这类返工的复现概率已经降低，不需要额外流程。

### 2.5 小结

四类里，2.1/2.2 是产品和质量的必要代价，2.4 规模小到可以忽略，**真正值得改的是 2.3**：30% 的会话是交接/核验性质，且审计明确指出这类任务的默认模型选择不合理。这是"贵在不该贵的地方"的具体所指，而不是笼统的"少用 Opus"。

## 4. 为什么用户感知接近于零

分三个角度回答，并明确区分这是产品策略问题、验收问题还是版本定义问题。

### 产品角度

三个门禁（`radarEnabled`/`radarAnalysisEnabled`/`radarRecommendationsEnabled`，见 §0 核验，三者互相独立无依赖）默认关闭是 `AGENTS.md`/`CLAUDE.md` 明确记载的既定策略，不是遗漏。但策略本身有一个结构性缺陷：**关闭是有的，"何时开"没有**。Release Contract 和 Traceability 反复写"生产入口 DISABLED"，但没有任何一处写"预计在 v0.9 的第几个波次开启"。审计五-9 已经指出这一点："功能开关关闭超过一个大版本应在 Release Contract 里写明预计开启版本，避免建好但一直不开"。

### 工程角度

代码、测试、人工验收三层全部做完，唯独没有做"生产开关翻转+真实用户使用+收集反馈"这一步。这一步不需要新写代码，只需要决策和执行，但恰恰是这一步决定了前面几万行代码是否产生价值。工程侧已经把球停在门口，缺的是有人去踢。

### 发布策略角度

`5db96f3`（07-30 GA 当天）新增的"晋升跟进"入口证明了一件事：即使在 GA 收尾阶段，团队仍在给一个**门禁关闭的功能**修 UX 缺口。这说明"渐进开关"策略执行中出现了注意力错配——投入继续流向用户看不到的功能，而不是流向"如何让已完成的功能被看到"。

### 三者定性

不是验收问题（人工验收标准明确且被满足了），主要是**发布策略问题**（渐进开关本身合理，但缺少开关时间表），其次是**版本定义问题**（v0.8 把"代码+测试+人工验收完成"等同于"版本完成"，但 Release Contract §4 自己的判定标准里第 6 条是"用户明确批准发布"——负责人确实批准了，可批准的是"接受风险发布"，不是"功能已产生价值"）。

### 避免再次出现的机制

给 Release Contract 加一条强制字段：任何默认关闭的门禁，必须同时写"预计开启版本"和"开启前置条件"。没有这两个字段的门禁不允许进入下一个 RC 冻结。

## 6. 过度工程化裁决

不单以文件数/行数判断，结合职责、复用和业务风险逐项回答：

**13 张新表是否有明确领域必要性？** 有必要性，但必要性不均。`radar_capture_sessions`/`snapshots`/`source_records`/`candidates`/`candidate_versions`/`candidate_sources` 六张是采集→版本化链路的直接载体，去掉任何一张都会破坏 RC-04 的不可变版本要求。`analysis_tasks`/`job_match_analysis_records`/`radar_recommendation_batches`/`radar_actions`/`radar_promotions` 五张分别对应 RC-07/08/10/11 四条独立业务链路，職責边界清楚（分析任务、推荐批次、用户动作、正式晋升不应该塞进同一张表）。`radar_rule_assessments` 和 v8 的 `radar_candidate_relations` 是规则证据和重复裁决的持久化，属于"如果不做，RC-05/06 的可解释性和防重复提示就没有承载"的刚需。**结论：13 张表没有明显的过度设计，都能对应到具体的 RC 项**，问题不在表的数量，在这些表背后的能力还没开放给用户。

**37 条 HTTP 路由是否与业务能力相称？** 19 条在 `routes.ts`（采集/评审/动作）、7 条分析、3 条推荐、8 条晋升。对照 5 个子域、12 个 RC 项，人均每个 RC 项 3 条路由左右（创建/查询/操作类的标准 CRUD-plus-action 模式），不算铺张。**相称**。

**117 个 Radar 文件是否存在过度拆分？** 拆分为根目录（采集/评审）+ action/analysis/promotion/recommendation 四个子域，每个子域内部是 service/repository/coordinator/schema/spec 的标准分层。这是"测试文件与实现文件一一对应"的自然结果（79 个新 spec 文件本身就占了一部分文件数）。审计没有发现同一职责被拆成多个文件的证据。**不构成过度拆分**，117 是"5 个子域 × 标准分层 × 含测试"的正常乘积，不是碎片化的信号。

**测试 churn 接近代码 churn 是质量优势还是维护负担？** 两者都是，但当前阶段质量优势更明显。对一个刚经历 schema v7→v8 生产升级、AI 结构化输出偶发截断的项目，1:1 左右的测试/代码比在 GA 前是合理的风险对冲。维护负担会在 v0.9 显现——如果 Radar 门禁常年不开，这 154 个 spec 文件里对应"关闭态"分支的测试会随着代码演进逐渐漂移而无人发现，因为没有真实流量会触发它们。**结论：现在是优势，如果门禁继续关闭超过一个版本会转为负担**，这是任务 5 止损线要覆盖的场景。

**Candidate/Version/Analysis/Recommendation/Promotion 分层是否合理？** 合理。这个分层直接对应 CLAUDE.md §5 明确写的架构边界（"RadarCandidate 只保存生命周期"、"标准化事实进入不可变 Version"、"收藏/忽略/重点/已投递从 RadarAction 派生"、"正式晋升从 RadarPromotion 派生"），不是本轮实施引入的新抽象，是产品在设计阶段就已裁决的边界，实施只是落地。**这不属于本次审计应该重新评估的对象**，因为它是需求本身，不是工程选择。

**哪些抽象现在产生价值？** BOSS 采集桥背后的 CaptureSession/Snapshot/SourceRecord 链路——因为 RC-01/02/03 是唯一门禁外、用户已在用的部分，这条链路上的抽象是唯一"现在"产生价值的。

**哪些抽象只有未来价值？** Candidate/Version 之上的 Analysis/Recommendation/Promotion 全部子域，包括对应的 9 张表、25 条路由（7+3+8+7 analysis 相关）、绝大部分组件。它们的价值完全取决于门禁何时打开、打开后用户是否真的使用。

**哪些抽象应该推迟到真正有第二个使用方时再做？** 没有发现"为假想的第二使用方"预先设计的抽象——13 张表全部对应已确定的 12 个 RC 项，不是为了未来扩展预留的空表。唯一接近"面向未来"性质的是 CodeGraph 本地索引接入，但审计已定性为"工程效率工具，非产品能力"，且规模极小（仅 `.gitignore` 约定），不构成过度工程化。**结论：v0.8 本身没有明显的过度工程化，真正的问题是"已经做的工程，还没有被验证"，这是发布节奏问题，不是设计问题。**

## 7. v0.9 模型预算规则

- **Sonnet 默认负责**：交接/接管类会话的起手核验（读交接文档、`git status`/`git log`、复述当前状态）；纯文档模板化同步（Traceability/Release Contract 格式更新）；常规功能实施（非架构裁决、非生产数据风险的日常编码）；测试编写与调试。
- **Haiku 负责**：无需推理的机械性操作——批量格式检查、简单 grep 式信息提取、状态回显类的确认消息。v0.8 期间 Haiku 用量极低（41 请求/¥0.35），v0.9 可以适度提高这类任务的分配比例，但不强制指标,因为多数任务复杂度超过 Haiku 适用范围。
- **何时允许升级 Opus**：核验过程中发现需要裁决生产数据库风险（如 schema 迁移、备份恢复策略）；架构歧义需要裁决（如是否新建表、是否拆分子域）；连续失败超过止损线（见任务 8）；用户直接要求。**接管/交接会话默认不得直接以 Opus 起手**，除非首条消息本身已经明确是生产风险裁决类任务（如本次审计中合理使用 Opus 的反例：接管生产库升级、接管 Provider 错误中断）。
- **Opus 在正常版本中的成本占比上限**：v0.8 的 90.6% 是"任务分类不清导致的默认档位过高"的结果，不是正常版本应有的比例。v0.9 目标：Opus 占比控制在 **60% 以下**（不是精确科学值，是基于"去掉 30% 交接类会话的默认 Opus 使用后自然下降的量级"做的合理估计，具体数字需要 v0.9 中期复核账单验证，不能只凭本报告一次性定死）。
- **单个功能超过多少轮失败必须暂停**：同一个功能点（如某个 API 端点、某个组件）如果连续 **3 次修复尝试后问题仍未解决**，必须暂停继续修补，改为专门开一次"根因定位"会话（不动代码，只诊断），参考本轮 DeepSeek 截断问题"先治标后治根"的经验——如果第一轮就假设"推理模型思维链挤占 max_tokens"，可以少走一轮。
- **交接会话超过多少次必须触发根因复盘**：同一个功能波次（V8-N 级别）如果交接/接管会话数超过 **2 次**，必须触发一次"为什么反复中断"的复盘，判断是外部原因（Provider 故障/额度耗尽，本轮至少 3 次属此类）还是内部原因（单次任务范围过大导致更容易撞额度上限，本轮审计未定论，需要在 v0.9 首次出现类似情况时专门验证）。

## 8. v0.9 Token 与会话止损线

由于无法拿到实时人民币数据，使用会话轮数、上下文规模、文件范围和失败次数作为代理指标。

| 任务等级 | 定义 | 止损线 | 触发后处理 |
|---|---|---|---|
| 小任务 | 单文件或紧密关联的 2-3 个文件；无架构裁决 | 用户轮次 > 30 或修复尝试 > 3 次仍未解决 | 停止继续修补，切换到诊断模式（只读，不改代码），定位根因后再决定是否继续或升级模型 |
| 中任务 | 单个波次内的功能实现（如一个 RC 项的服务层+路由+前端组件） | 单会话时长 > 4 小时（对照本轮 V8-1/V8-6 起手会话已超此线，说明这类"设计密集"任务本身可能需要拆分为多个会话而非一次扛完）或交接次数 > 2 次 | 触发任务 7 的"交接次数复盘"；评估是否应该把任务拆得更小 |
| 高风险任务 | 涉及生产数据库、生产开关翻转、AI Provider 契约变更 | 任何失败或歧义都必须停止并升级到 Opus 裁决，不设"轮数"止损（错误代价远高于讨论成本，参考审计"没有发现讨论很久但改动价值很低的反例"的结论） | 强制人工确认后才能继续，不允许自动重试绕过 |

止损触发后的统一处理流程：暂停当前修补路径 → 用只读方式（读日志、读代码、读交接文档）定位根因 → 写入 memory 或临时诊断记录 → 明确说明"为什么之前的做法不对"→ 如果需要偏离原计划，先向用户确认再继续（对齐 CLAUDE.md 全局规则"若方法已失败两次，需诊断根因而非继续小修小补"）。

## 9. v0.9 功能与发布门禁

**一个版本允许多少个主用户结果？** v0.8 定义了 12 个 RC 项，实际只有 3 项（RC-01/02/03）走到"用户实际产生价值"。v0.9 应该反过来：**先定几个能在本版本内走完"代码→测试→验收→开关→真实使用→反馈"全链路的主结果，数量控制在 2-3 个**，而不是像 v0.8 一样五个波次全部完成工程侧但只有一个走完全链路。

**内部工程能力与用户可见功能的比例？** v0.8 的比例严重失衡（8 项工程完成 vs 3 项用户可见）。v0.9 的目标不是消灭内部工程投入（RC-09/RC-12 这类基础设施仍然需要），而是**新增的内部工程投入必须能在同一版本内看到至少一次真实开关翻转**，否则应该归入"暂缓"而不是"完成"。

**什么情况下禁止新增新表？** 在 Radar 现有 13 张表对应的能力（评审/分析/推荐/晋升）里，任何一项还没有真实用户开关验证之前，禁止新增支撑 Radar 新子能力的表。例外：修复现有表的数据完整性问题（如加索引、加约束）不算"新增能力"，不受此限制。

**什么情况下禁止新增新抽象？** 在没有第二个真实使用场景（第二个用户、第二种岗位来源、第二种 AI Provider 等）出现之前，禁止为"未来可能需要"预先设计通用层。v0.8 的 13 张表全部对应已确定需求，这个纪律本身在 v0.8 执行良好（任务 4 已确认），v0.9 应该继续保持，不因为"感觉可能需要"而破例。

**什么情况下禁止"顺手重构"？** 任何门禁仍关闭的功能，在没有真实用户反馈之前禁止对其做用户体验类重构（`81cc4d8` 单岗位分析面板重构、`eb43f1a` 降噪虽然规模小，但方向是"在没人用的功能上花时间打磨"，v0.9 应避免在开关前继续这类投入，除非是修复已发现的缺陷）。

**功能完成后多久必须进入真实用户可用状态？** 建议：功能代码+测试+人工验收完成后，**进入下一个版本周期（即最多跨 1 个大版本）内必须决定开或不开**，不能无限期停留在"完成但关闭"。

**默认关闭的功能必须写明预计开放版本？** 是，强制。这是 §4 已经给出的具体机制，本节重申为发布门禁规则：任何 Release Contract 条目标记为门禁关闭时，必须同时填写"预计开启版本"字段，缺失该字段视为条目未冻结完成。

**一个核心功能允许跨多少个版本保持关闭？** 建议上限 **1 个大版本**（即 v0.8 关闭的功能，最晚应在 v0.9 内做出"开启"或"正式放弃/降级为 v1.0 议题"的裁决，不允许跨到 v1.0 仍处于"关闭中"的模糊状态）。

**什么时候应判定该功能投入暂时失败？** 如果到了预定开启版本，开关翻转后的真实使用反馈显示核心假设不成立（例如用户打开 Radar 后完全不用，或分析结果的可信度反馈持续为负），应判定为"暂时失败"，转入重新设计而非继续在原假设上打磨。目前 v0.8 尚未走到这一步（因为还没开过），这是 v0.9 需要产出的新证据，本报告无法预判结论。

## 10. v0.9 推荐实施顺序

1. **先开 `radarEnabled`（在受控范围内），验证 BOSS 采集桥之后的评审工作台是否被真实使用**。这是唯一能把 8 项"已完成但零感知"的工作转化为真实反馈的动作，且不需要新写代码，只需要决策+受控发布。
2. **视 1 的反馈决定是否开 `radarAnalysisEnabled`**。单岗位分析是 v0.8 里 token/成本投入最高的部分之一（含 DeepSeek 截断诊断成本），如果评审工作台本身用户不买账，不必急着开分析门禁。
3. **修复优先于新功能**：vitest 并发超时配置（低成本、审计已给出具体建议）应该先修，避免未来把资源争用误判为真实回归。
4. **30 条真实评测和核心页面截图/文案验收应该推进，但推进方式是解决"数据与人工标注"阻塞本身，不是绕过它**——不能靠追加工程投入替代真实评测。
5. **暂缓 `radarRecommendationsEnabled` 和 RC-09（误区诊断）**，直到 1、2 有明确反馈。推荐批次和误区诊断都依赖候选池已经积累了真实评审数据，过早开放没有意义。
6. **RC-12 剩余的可靠性/发布闭环工作**（人工确认部分）跟随 30 条评测的进度同步推进，不单独提速。

### 明确回答特别问题

- **v0.9 是否应该先做新功能？** 不应该。优先级 1-2 已经说明：先把 v0.8 已完成的能力变成有反馈的能力，再决定新功能方向，否则会重复"完成一个版本但核心功能没开放"的模式。
- **是否应该先打开 Radar 门禁？** 应该，且是 v0.9 第一优先级（见上）。
- **是否需要先完成真实岗位评测？** 需要，但"先完成"和"先启动"不同——评测数据和标注的阻塞不会因为延后而自动解除，应该与开关验证并行推进，而不是等评测完成后再开门禁（两者互相提供输入：真实使用产生的候选池本身可以部分构成评测样本来源）。
- **是否应该引入 Spec Kit Lite？** 不建议在 v0.9 引入。当前问题不是"缺少规格化流程"，而是"已有规格（Release Contract/Traceability）执行到位但发布节奏错位"。引入新流程工具会增加而不是减少当前的结构性问题。
- **是否应该引入 LangChain？** 不应该。AGENTS.md §12 已经明确禁止引入 LangGraph/CrewAI/AutoGen 类框架，未经批准不得引入新 AI Provider 或做 BYOK；当前 AI 需求（结构化单岗位分析）用直接 Provider 调用 + Envelope/Payload 分离已经满足，没有出现"链式多步骤 AI 调用"或"多 Agent 协作"的真实需求去证成引入编排框架的必要性。
- **是否应该建设自研 LLM Runtime？** 不应该。v0.8 已经通过"确定性任务 ID + 状态机 + 一次结构修复 + 进程恢复"解决了当前规模下的可靠性需求（RC-12 已实现部分），没有证据显示当前吞吐量或并发需求超出这套方案的能力边界，自研 Runtime 属于典型的"面向未来价值"投入，应推迟到真正出现第二个 Provider 或显著更高并发需求时再评估。
- **哪些事情如果同时做会导致范围再次失控？** 同时开三个门禁（Radar+Analysis+Recommendation）且同时启动新功能开发且同时推进 30 条评测——这正是 v0.8 的模式（五个波次并行推进，工程侧全部按时交付，但没有一个节点停下来做真实验证）。v0.9 如果重复"多线并行全推进"，会再次得到"投入很大、验证为零"的结果。
