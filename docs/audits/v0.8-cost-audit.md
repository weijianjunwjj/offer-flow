### 口径差异说明（重要，必须明确声明）

- 本机会话日志中按 model 字段聚合出的 token 总量（input+output+cache_creation+cache_read）约为 **2030.9M**，是用户提供账单数据（991.97M）的约 **2.05 倍**。

## 五、重点回答

**1. v0.8 最终增加了哪些真正能力？**
代码和领域模型层面，V8-1~V8-6 全部完成：BOSS 当前页/批量采集桥、候选评审与重复裁决工作台、单岗位 AI 分析、推荐批次、正式晋升与反向追踪，共 37 条新 API、12+1 张新表、117 个 `server/radar/` 文件、9 个新前端组件。这些能力在代码层"真实存在且测试通过"。**但用户在 v0.8.0 GA 发布时实际能用到的新增能力是 0**——`radarEnabled`/`radarAnalysisEnabled`/`radarRecommendationsEnabled` 三个门禁全部默认 `false`（1.6 节已核验），这是 CLAUDE.md §3 明确记载的既定策略（按开关启用），不是遗漏。

**2. 哪些能力看似工作量很大，但用户感知很弱？**
评审工作台（V8-3，13 次迭代、churn 前列）、单岗位分析面板（V8-4）、推荐批次（V8-5）、正式晋升追踪（V8-6）——四者都完整实现、测试齐全，但因门禁关闭，v0.8.0 GA 发布当天对普通用户是不可见的。这是本轮工作量与短期感知落差最大的部分，但**这个落差是产品策略选择（渐进开关）造成的，不是工程浪费**。

**3. 哪些时间花在了合理的底层建设？**
schema v7→v8 领域模型设计与迁移（含 selftest、备份验证、dry-run 演练）、`radar_candidate_relations` 重复裁决表设计、5 个子域（action/analysis/promotion/recommendation + 核心）的服务层拆分。这些是没有捷径的必要投入——领域模型定义清楚了，后续每个子域才能独立按波次交付而不互相冲突。

**4. 哪些时间明显花在了返工、重复读取、过度设计和重复审计？**
- DeepSeek JSON 截断问题的第一版"处理非法响应"（`0c55d29`）在根因修复（`60dbbbd`）之前提交，是一次诊断返工，但规模可控（当天完成）。
- 12 次接管/交接会话的状态核验开销是结构性的，其中至少 3 次是被动触发（Provider 400 错误、额度耗尽），本身不是"过度设计"，但确实是本轮协作模式下无法避免的固定摩擦成本。
- 未发现"重复审计"或"多次重复总结同一结论"的证据——子代理使用率很低（15 次/13646 条消息），没有大规模"分派再汇总"模式。

**5. Opus 4.8 为什么占总费用约 90.6%？**
从会话原始 token 占比看，Opus 4.8 占 86.1%（口径见三节说明，方向与账单一致）。核心原因：本轮 40 个会话里，绝大多数深度实现类会话（V8-1 领域建模、V8-3 评审工作台、V8-6 晋升领域、生产库升级接管）默认使用 Opus，只有极少数纯文档/纯 Sonnet 会话（如 07-17 的 `11441af9`）不涉及 Opus。Opus 单条消息的 token 消耗（含 cache_creation/cache_read）也显著高于 Sonnet/Haiku——本轮 Opus 平均单条消息 tokens 约为 Sonnet 平均值的数倍（1749.0M/11375条 ≈ 154K/条，对比 Sonnet 170.4M/1403条 ≈ 121K/条，加上 Opus 调用量本身是 Sonnet 的 8 倍），量价双重叠加导致占比集中。

**6. 是否存在"大量 Token 消耗，但最终 diff 很小"的任务？**
`557295d4`（07-27，2606 分钟，317.1M token）对应的提交是 V8-6 晋升领域的服务层落库（幂等设计、四个 HTTP 接口）——这类"设计密集但代码量未必大"的任务，token/diff 比值天然偏高，但**不能等同于浪费**，因为幂等键设计错误的后果（并发冲突、数据不一致）远比多花 token 讨论清楚更贵。`15f85139`（07-20，1342 分钟，322.3M token）同理，是 V8-1 领域模型的起手设计。**没有发现"讨论很久但最后只改了几行代码且改动价值很低"的反例**。

**7. 如果重新做一次 v0.8，哪些步骤应该删除、合并或降级模型？**
- 交接/接管类会话（12 个）中的"核验磁盘状态、复述理解"步骤可以降级为 Sonnet 5，只在需要裁决歧义时升级到 Opus，预计可降低这部分（约占会话数 30%）的模型成本。
- DeepSeek 截断问题的第一版"处理非法响应"可以合并：如果一开始就假设"推理模型的思维链会挤占 max_tokens"这条经验规则（现已写入 memory），可以少走一轮诊断。
- 纯文档模板化同步（Traceability/Release Contract 的格式化更新）可以考虑用脚本生成骨架 + Sonnet 填充，而非全程 Opus。

**8. 根据最终成果，700 元成本属于合理、偏高还是严重失控？给出依据。**
依据：100 个提交、47809 行净新增（代码 21200 + 测试 17442 + 文档 8443 + migration 1134，churn 口径）、37 条新 API、13 张新表/索引、9 个新组件、79 个新测试文件、1 次生产库受控升级、6895 次请求覆盖 10+ 天的连续开发——**从工作量密度看，700 元（≈6895 请求，人均单次请求成本约 0.103 元）不属于"严重失控"**。但也不属于"明显偏低"：Opus 占比 90.6% 的费用对应的产出中，评审工作台+分析+推荐+晋升四大能力全部因门禁关闭而"用户不可见"，如果只看 v0.8.0 GA 发布当天的可感知增量，700 元换来的直接可见变化很少（主要是采集桥）。**综合判断：属于"合理偏高"区间**——工程质量和测试覆盖率不差（vitest 1506 用例、vue-tsc 零错误），但模型选型（大量交接场景用 Opus）和产品策略（大量功能延迟开关）共同导致了"高投入、低即时可见产出"的错觉，实际是为 v0.9 及后续开关铺垫的正常基础设施投入，只是需要用更长的时间窗口衡量才合理。

**9. v0.9 硬性预算和自动止损规则（建议，需用户裁决是否采纳）**

- **模型分级规则**：交接/接管类任务（首条消息为"接管中断任务"/"交接"/"继续上一轮"性质）默认用 Sonnet 5 起手做状态核验，只有在核验过程中发现需要裁决生产数据风险或架构歧义时才主动升级到 Opus。
- **诊断先行规则**：遇到重复失败（如本次 DeepSeek JSON 截断），先花一次会话专门定位根因并写入 memory，再动代码修复，避免"边猜边改"式的多轮返工。
- **门禁上线周期规则**：功能开关关闭超过一个大版本（如本次 v0.8 全部门禁延续到 v0.9）应在 Release Contract 里明确写"预计开启版本"，避免"建好但一直不开"的投入被无限期搁置而失去可衡量的 ROI 锚点。
- **测试超时规则**：`npx vitest run` 全量并发下有 4 个测试因 5000ms 超时失败（复测通过），建议给涉及 Fastify+SQLite 集成测试的文件提高单测超时或限制 vitest 并发线程数，避免未来把资源争用误判为真实回归而触发不必要的排查。
- **会话数量止损线**：单个功能波次（如 V8-N）如果交接/接管会话数超过 2 次，应触发一次"为什么反复中断"的根因检查（本次至少 3 次是 Provider 侧 400 错误/额度耗尽，属外部原因，但仍值得追踪是否有可控因素，如单次任务范围过大导致更容易撞额度上限）。
