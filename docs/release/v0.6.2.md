# OfferFlow v0.6.2 Release Notes

## 版本定位

v0.6.2 是进入 v0.7 前的稳定性收口版本，只处理 SQLite migration、tracked snapshot 一致性、App 版本口径和 Human-in-the-loop 文档边界，不包含任何 v0.7 业务实体或功能。

## SQLite migration 基础

- 新增单调递增、固定顺序的 migration runner 和 `schema_migrations` 执行记录。
- migration 1（`001_v0_6_baseline`）承接当前四张 v0.6.x 表；全新数据库可从零初始化，现有数据库通过 `CREATE TABLE IF NOT EXISTS` 安全建立 baseline。
- 每条 migration 的结构变更、执行记录和兼容 `app_meta.schema_version` 更新在同一事务内完成；失败时整体回滚，重复启动不重复执行。
- 当前数据库 migration/schema 版本仍为 `1`，没有创建 v0.7 业务表。

## snapshot 一致性修复

修复前，本地 SQLite 有 12 个 Job，tracked snapshot 有 11 个。审计确认：

- 1 个 Job 只存在于 SQLite。
- 2 个同 ID Job 的 SQLite 记录更新时间更晚、稳定内容 hash 不同。
- profile 和 import_log 的集合与稳定 hash 一致。
- snapshot 的导出时间早于上述 SQLite 更新，现有“双方有 `updated_at` 时较新记录胜出”的规则会保留 SQLite 新版本；本次差异属于 snapshot 未及时刷新。

在备份验证完成后，通过正式 `db:sync` 路径保留 SQLite 中的唯一记录和较新记录，并重新原子导出 snapshot。修复后 profile 1、Job 12、import_log 1 的 ID 集合和稳定 hash 全部一致；实际 snapshot 已成功导入临时数据库，再次导出的三张业务表语义一致。

## App 版本统一

- `package.json` / `package-lock.json` 根项目版本：`0.6.2`
- UI / README 当前 App 版本：`v0.6.2`
- snapshot / manifest `appVersion`：`0.6.2`
- `OFFER_FLOW_JSON.version`：仍为协议版本 `0.2.0`
- SQLite migration/schema 版本：仍为数据库版本 `1`

## Review 边界校正

- 普通 LLM 岗位分析：先展示 AI 原文和解析预览，用户点击“确认并保存分析结果”后才写入岗位记录；当前不会进入 `reviewStatus=pending_review`，也没有正式 `ReviewRecord` 历史。
- JD 导入草稿：`importedDraft -> pending_review -> confirmed / deferred / rejected`；`deriveDecision` 对 pending review 派生 `manual_review`，当前主要保存最终状态。
- 两条路径都保留 Human-in-the-loop，但实现机制不同；均不会自动发送、投递或联系 HR。
- v0.7 计划让画像变更和策略建议采用正式提案审核记录，本版本未实现该能力。

## 数据备份与兼容

- 写入真实 SQLite 和 tracked snapshot 前，使用仓库现有 ignored `backups/` 机制生成时间戳备份。
- SQLite 备份通过 `integrity_check=ok` 和外键检查；snapshot / manifest 可解析且 manifest hash 与 snapshot 文件一致。
- 备份时未发现 SQLite WAL/SHM sidecar。
- v0.6.x 原有 profile、Job 和 import_log 数据均保留；migration 前后业务数据数量与关键 ID 不变。

## 明确未包含

本版本未开发 Application、MarketFeedbackEvent、Interview / Offer 新实体、动态岗位画像、主动策略引导、Agent、RAG、LangGraph 或多 Agent；未接入新 LLM Provider、BYOK、Boss 自动化，也未重构 BattlefieldPage 或全仓 API DTO。
