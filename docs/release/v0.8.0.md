## 1. 用户可见变化

- **当前页采集桥（浏览器扩展）**：在 BOSS 岗位详情页或通用网页点击一次扩展图标，
  读取当前标签页的 URL / 标题 / 可见文本进入 OfferFlow 预览，用户确认后才写入；
  不自动搜索、翻页、后台扫描，也不读取 Cookie / 密码 / Token。
- **可解释单岗位分析**：输出四档建议、匹配维度、证据、反证、缺口、风险与不确定性，
  结论先行、渐进披露；分析结果在用户确认前不进入正式记录。
- **推荐批次**：从用户勾选的岗位集合收敛出 0～8 条重点机会，附误区结果或证据不足提示。
- **雷达动作与正式晋升**：收藏 / 忽略 / 重点 / 已投待反馈及撤销以 Action 流水保存；
  高价值进展或用户明确要求后，可预览并幂等关联 / 创建正式 Job、Application、FeedbackEvent。
- 以上雷达类能力**随 v0.8.0 发布但默认关闭**，需按「§4 功能开关」显式启用。

> 说明：v0.7 起已开放的岗位匹配画像、能力基线、历史补录、市场位置、求职策略等正式能力保持不变。

## 2. 核心工程变化

- **持久化分析任务**：单岗位分析任务持久化、幂等、明确失败、支持取消、刷新恢复与重启后记录恢复。
- **结构修复 + 具体失败摘要**：岗位分析对非法 JSON 响应做一次结构修复；失败时给出具体失败摘要
  （区分截断 / 空内容 / 网络 flake / 结构非法），不再是笼统报错。
- **非法 JSON 根因收口**：对推理型模型关闭思维链，避免思维链吃光 token 预算导致答案 content 为空、
  JSON 非法；脚本层对瞬时网络 flake 有界自动重试，绝不重试确定性失败（截断 / 空内容 / HTTP / 限流 / 取消）。
- **有界人工重试与人工恢复任务**：撞人工重试硬上限（6/6）的 failed 任务，改为新建关联的恢复任务
  （复用冻结输入、派生新 taskId），**旧失败任务保留为不可变审计历史，绝不 UPDATE / 重置**。
- **单岗位分析面板重构**：四层优先级（结论 → 四维匹配 → 关键约束/风险 → 补充信息），语义色 + 渐进披露。
- **本地地址**：本地前端 http://localhost:5173 ，本地 API http://127.0.0.1:17365 。

## 3. 数据库升级

- **目标 schema：v8（migration 1..8）**。生产库已于受控流程中升级 v7→v8，仅新增
  `radar_candidate_relations` 表（含索引）与 `radar_rule_assessments.evidence_json` 列，既有业务行数逐一不变。
- `PRODUCTION_SCHEMA_VERSION` 常量仍为 2（生产底座下限语义），`LATEST_SCHEMA_VERSION = 8`。
- 真实库不会自动迁移：启用生产 Radar 需真实库 schema ≥ v8，否则服务拒绝启动。
- **从任何旧版本升级前必须先创建一致性备份**，并在真实库副本上演练迁移后再切换（见「§6 升级步骤」）。

## 4. 功能开关（默认全部关闭）

岗位雷达类能力**随 v0.8.0 发布但默认关闭**，按开关启用。前端为构建期开关（`VITE_*`），
后端为运行期环境变量，两侧需成对开启，否则会出现「前端有入口、后端 404」。

| 能力 | 前端（构建期） | 后端（运行期） | 默认 |
|---|---|---|---|
| 岗位雷达采集桥 | `VITE_OFFERFLOW_RADAR` | `OFFERFLOW_RADAR` | 关闭 |
| 单岗位分析 | `VITE_OFFERFLOW_RADAR_ANALYSIS` | `OFFERFLOW_RADAR_ANALYSIS` | 关闭 |
| 推荐批次面板 | `VITE_OFFERFLOW_RADAR_RECOMMENDATIONS` | —（随雷达网关自动接线） | 关闭 |

- 后端 `OFFERFLOW_RADAR=true` 时，真实库 schema 必须 ≥ v8，否则**拒绝启动**并提示先经授权升级。
- `OFFERFLOW_RADAR_ANALYSIS` 依赖 `OFFERFLOW_RADAR`；仅开分析未开雷达时分析路由不注册。
- 推荐 / 动作 / 晋升 / 追踪不新增开关，沿用雷达路由内既有 schema / analysis 门禁自动接线。
- 启用值为字符串 `true`（大小写不敏感），其余值或留空按关闭处理。

启用示例（本地开发，成对开启雷达 + 分析）：

```bash
VITE_OFFERFLOW_RADAR=true VITE_OFFERFLOW_RADAR_ANALYSIS=true \
OFFERFLOW_RADAR=true OFFERFLOW_RADAR_ANALYSIS=true npm run dev
```

## 6. 升级步骤

> 真实生产 migration 需用户明确授权；以下为标准受控流程，完整细节见
> [Migration & Recovery Runbook](../runbooks/offerflow-v0.8-migration-recovery.md)。

1. **备份**：`npm run db:backup` 创建一致性备份（含 SHA-256 指纹、integrity、foreign-key 校验）。
2. **副本演练**：在真实库副本上 dry-run 升级：`npm run db:upgrade-real`（不带 `--confirm` 只打印计划、不写入）。
3. **校验演练结果**：`npm run migration:selftest` 与 `npm run db:doctor` 均通过。
4. **升级生产**（授权后）：`npm run db:upgrade-real -- --confirm`
   （建议附 `--expected-source-fingerprint <指纹>` 做预期指纹校验）。
5. **升级后核验**：`npm run db:doctor`（integrity ok、0 外键违规），确认 schema=v8、既有业务行数不变。
6. **应用侧**：拉取 v0.8.0 代码后 `npm install`（lockfile 已锁 0.8.0），`npm run build`。
7. **浏览器扩展**：`npm run extension:build` 后在 `chrome://extensions` 重新加载 `browser-extension/` 目录。
8. **启用雷达（可选、需授权）**：按「§4 功能开关」成对设置前后端开关；不启用则维持默认关闭。

## 7. 回滚步骤

> 完整触发条件与步骤见 Runbook §8。**不采用逆向 `DROP TABLE` / 猜测性 UPDATE**，恢复完整一致性备份更可靠。

1. 停止应用；
2. 保存失败数据库副本用于调查；
3. 用 pre-v0.8 一致性备份替换生产库；
4. 校验 hash、integrity、foreign keys；
5. 启动 v0.7 兼容应用版本；
6. 验证正式版本与 Job / Application / FeedbackEvent；
7. 记录失败原因，禁止在生产库上直接试错。
