## 1. 发布契约摘要

### 1.1 v0.8 必须交付的 12 项用户结果

1. 用户可在 Chrome / Edge 中主动采集当前 BOSS 岗位页面。
2. 非 BOSS 页面可通过“通用可见文本”当前页降级采集；失败时可粘贴文本。
3. 用户可粘贴一条原始 JD 文本，进入统一预览、纠错和确认流程。
4. 系统保存不可变原始快照、来源身份、标准化候选和不可变 CandidateVersion。
5. 系统识别确定重复、疑似重复、未变化和实质变化；未变化不重复分析。
6. 系统以透明规则区分硬约束、高风险、一般偏好和状态抑制，并展示命中原文与用户覆盖入口。
7. 系统复用 v0.7 正式画像，对单岗位输出可解释四档建议；AI 事实、推断、风险、反证和不确定性分层展示。
8. 系统从用户选择的一批岗位中收敛输出 0～8 条重点推荐，允许 0 条，不得凑数。
9. 每个推荐批次输出一个诊断结果：证据充分时指出主要筛选误区；证据不足时输出“暂不形成正式误区诊断”及缺失证据。
10. 用户可执行收藏、忽略、恢复、重点处理和“已投递待反馈”；这些行为不自动污染正式求职样本。
11. 出现高价值现实反馈或用户明确要求后，系统可幂等晋升现有 `Job / Application / FeedbackEvent`。
12. 分析任务支持持久化、幂等、明确失败、一次结构修复、手动重试、取消、页面刷新恢复、进程重启后的记录恢复与可重试失败，并通过评测、migration、备份和恢复验收。

### 1.2 明确不承诺

v0.8 不承诺：

- 猎聘专用字段适配；
- 自动登录、自动翻页、后台扫描或定时运行；
- 读取或保存 Cookie、密码、Token、完整浏览历史；
- 绕过验证码、登录验证或平台风控；
- 自动打招呼、联系招聘方或投递；
- 岗位下架与恢复的持续检测；
- 后台来源调度与定时发现；
- 从反馈自动进化画像；
- 完整 Agent Runtime、独立 Worker、消息队列或真正的 LLM 请求断点续跑；
- 多用户、多租户、跨设备同步与公网商业化部署；
- PostgreSQL、Redis、BullMQ、pgvector、微服务或 Kubernetes；
- 精确预测回复率、面试率、Offer 率或薪资概率。

### 1.3 范围变更规则

任何删除、延期、拆分或降级 1.1 中用户结果的决定，必须获得用户明确批准。

技术阶段性完成不等于产品结果完成。以下情况不得宣称 v0.8 完成：

- 扩展能读取页面，但不能进入预览和候选；
- 表已创建，但用户仍需反复截图；
- AI 返回自由文本，但没有结构校验与证据引用；
- 有推荐列表，但没有 0～8 条收敛与空推荐；
- “已投递待反馈”仍偷偷创建正式 Application；
- 页面刷新后任务消失；
- 旧分析混入新推荐；
- 误区诊断在证据不足时仍强行锐评；
- P0 用户结果被技术讨论静默移到后续版本。

- Structured Output、Zod、一次结构修复、输入指纹、版本冲突、幂等与 Human-in-the-loop；
- SQLite migration、生产备份与恢复。

v0.7 回答：

> 我是谁、我稳定拥有哪些能力、在不同城市当前大概能争取什么，以及阶段策略是什么。

### 2.2 v0.8 要补上的断层

现实求职仍存在四个断点：

1. 真实 JD 进入系统摩擦高；
2. 同一岗位反复出现，用户重复消耗注意力；
3. 正式画像尚未稳定参与“今天先处理哪几个”的具体决策；
4. 投递无回复若直接进入正式 Application，会污染样本。

v0.8 回答：

> 我主动看到的这些真实岗位，哪些值得先处理，为什么？  
> 哪些只是重复出现或没有变化？  
> 我是否正在把注意力投向错误岗位族？  
> 无回复投递如何不污染正式判断？

## 3. 产品定位与核心价值

### 3.1 产品定位

**可解释岗位雷达与 JD 采集桥。**

v0.8 不是招聘爬虫，也不是第二套岗位台账。它连接：

```text
v0.7 已确认职业画像
        ↕
用户主动看到的现实岗位
```

### 3.2 核心价值

1. 降低真实岗位进入系统的摩擦；
2. 避免反复阅读相同岗位；
3. 用透明规则先挡掉明显低价值岗位；
4. 用 AI 映射已确认能力证据，而不是复述 JD；
5. 把几十条岗位压缩成有限行动队列；
6. 让用户看见本批注意力偏差；
7. 保护正式求职记忆不被浏览、忽略和无回复污染；
8. 证明 OfferFlow 是可靠 AI 应用，而不是 CRUD 上贴一颗模型按钮。

### 3.3 相邻版本边界

| 版本 | 核心问题 | 主要输出 |
|---|---|---|
| v0.7 | 我是谁、市场位置与阶段策略是什么 | 正式画像、能力基线、市场位置、策略窗口 |
| v0.8 | 我主动看到的岗位哪些值得处理 | 采集桥、候选版本、规则、分析、有限推荐、雷达动作 |
| 已退役方向 | 持续主动发现新增岗位 | 相关来源配置、增量运行与持续简报已于 2026-08-27 退役 |
| v1.0 候选 | 如何成为长期可部署的职业操作系统 | 同步、部署、长期数据治理与复盘 |

## 4. 冻结产品原则

### 4.1 三层严格分离

```text
来源层
CaptureSnapshot / SourceRecord
        ↓
雷达层
Candidate / CandidateVersion / RuleAssessment / Analysis / RecommendationBatch / Action
        ↓ 用户明确确认或出现高信息量反馈
正式记忆层
Job / Application / FeedbackEvent
```

禁止新增：

- `Opportunity`；
- 与 Application 平行的轻量正式流程；
- 与 FeedbackEvent 平行的反馈时间线；
- 第二套岗位画像、能力基线、市场位置或策略版本体系。

### 4.2 当前页采集必须由用户主动触发

- 只处理当前标签页；
- 只读取当前 URL、标题和可见/可提取岗位内容；
- 不读取 Cookie、密码、Token 与完整历史；
- 不自动翻页、遍历、定时或后台扫描；
- 采集结果进入预览，用户确认后才正式写入；
- 外部页面内容一律视为不可信数据。

### 4.3 原始快照与标准化事实并存

系统必须同时保留：

1. 不可变原始 `RadarCaptureSnapshot`；
2. 不可变标准化 `RadarCandidateVersion`。

字段无法可靠识别时保持未知，不得由 AI 或规则补造事实。

### 4.4 Candidate 只保存生命周期

`RadarCandidate.lifecycle_status` 只允许：

- `active`；
- `merged`；
- `archived`。

分析状态从任务与分析记录派生；收藏、忽略、重点与已投递从 Action 派生；晋升从 Promotion 派生。

### 4.5 所有判断绑定明确 CandidateVersion

以下对象必须引用 `candidate_version_id`：

- 规则评估；
- 用户规则覆盖；
- AI 分析；
- 雷达动作；
- 推荐批次；
- 正式晋升。

手动纠错与 JD 实质变化都生成新版本，不覆盖旧标准化事实。

### 4.6 规则先筛，AI 再解释

```text
数据质量
→ 硬约束
→ 风险与偏好
→ 状态抑制
→ AI 证据映射与隐性风险解释
```

AI 不得推翻用户已确认硬约束。规则与 AI 冲突时同时展示，由用户裁决。

### 4.7 推荐有限，允许空推荐

- 每批最多 8 条；
- 目标 3～8 条但不得凑数；
- 同公司高度相似岗位默认只占一个位置；
- 已忽略、已投递待反馈或已晋升且内容未变化的岗位默认抑制；
- 内容实质变化后可重新进入，但必须展示变化。

### 4.8 误区诊断必须有证据门

每批必须输出一个“诊断结果”，而不是必须强行输出一个误区：

- 证据充分：输出一个主要误区；
- 证据不足：输出 `insufficient_evidence`、缺失证据和下一步收集建议。

诊断只描述本批筛选行为，不形成长期人格或职业判决。

### 4.9 “已投递待反馈”不是正式 Application

它只是一条 `RadarAction`，用于：

- 短期去重；
- 跟进日期；
- 防止重复推荐；
- 保留用户现实动作。

无回复不是拒绝，也不是能力反证。

### 4.10 AI Payload 与系统 Envelope 分离

AI 只返回分析内容，不返回：

- candidateId；
- candidateVersionId；
- contextVersions；
- ruleVersion；
- promptVersion；
- inputHash；
- model。

这些由服务端确定性附加到分析记录 Envelope。

### 4.11 历史分析不可变，是否过期确定性派生

旧分析保留。系统比较分析 Envelope 与当前 CandidateVersion、正式画像版本、规则和 Prompt 版本，得到：

- `current`；
- `stale`；
- `staleReasons[]`。

推荐批次默认不得使用 stale 分析，除非明确标记为旧版本参考。

### 4.12 排序分不是概率

任何内部排序分：

- 只用于当前候选集排序；
- 不是 Offer 概率；
- 不是薪资估值；
- 不是个人价值评价；
- 页面不能只展示一个神秘总分。

## 5. 输入准备度与城市降级

### 5.1 正式输入要求

| 输入 | 要求 | 缺失行为 |
|---|---|---|
| ResumeVersion | 必须 | 阻断 AI 分析 |
| JobMatchProfileVersion | 必须 | 阻断 AI 分析 |
| CapabilityBaselineVersion | 可缺失 | 允许探索性分析，置信度最高为 medium |
| MarketPositionVersion | 可缺失 | 不形成强市场层级和供给判断 |
| StrategyVersion / StrategyWindow | 可缺失 | 不形成强阶段策略判断 |
| 城市专属画像 | 可缺失 | 使用全局画像，`cityCode=null`，显示城市证据不足 |

### 5.2 非苏锡沪杭岗位

- 不默认硬阻断；
- 使用全局岗位画像；
- `cityCode=null`；
- 页面展示“缺少该城市正式市场画像”；
- 城市与薪资结论降低置信度；
- 只有命中用户明确城市硬约束时才阻断；
- 当前策略范围之外可作为风险，而不是伪装成客观不适合。

### 5.3 岗位输入最低准备度

以下情况阻断 AI 深度分析，但仍保存候选：

- 原始岗位文本为空或明显不是岗位；
- 岗位职责与要求均无法识别；
- 页面文本仅包含导航、广告或推荐列表；
- 数据质量冲突严重到无法判断岗位主体。

系统应给出需要补充或向 HR 核验的字段。

## 6. P0、P1 与后续边界

### 6.1 P0：v0.8.0 必须完成

#### P0-01 BOSS 当前页主动采集

- Chrome / Edge；
- 用户点击后读取当前页；
- 提取 URL、标题、可见文本、稳定来源 ID 与可可靠识别字段；
- 进入预览，不能直接写正式数据。

#### P0-02 通用可见文本降级采集

- 对非 BOSS 页面读取当前页 URL、标题和可见文本；
- 不承诺平台专属字段完整度；
- 无法识别字段保持未知；
- 仍进入统一预览和纠错。

#### P0-03 采集入口收敛与统一预览

- 只接受浏览器扩展当前页采集；
- 不提供手工 JD 文本、链接组合或 JSON 对象/数组输入；
- 统一 preview → correction → commit；
- 不建立长期导入批次页面与领域表。

#### P0-04 原始快照与来源身份

- 不可变 CaptureSnapshot；
- RadarSourceRecord；
- Provider 与版本元数据；
- 首次发现、最近发现、最近变化；
- 原始来源可追踪。

#### P0-05 Candidate 与 CandidateVersion

- Candidate 仅保存生命周期；
- active_version_id；
- CandidateVersion 不可变；
- 手动纠错与实质变化创建新版本；
- 旧版本可回溯。

#### P0-06 标准化、质量、重复与变化

- 标准字段与 Zod 校验；
- 数据质量问题；
- 稳定来源 ID、规范化 URL、内容指纹与相似度；
- 确定重复、疑似重复、未变化、实质变化；
- 疑似重复不得静默合并。

#### P0-07 透明规则预检

覆盖：

- 外包、派遣、驻场；
- 低薪、通勤、学历与经验硬门槛；
- 纯维护、纯切页面、短期救火；
- 前端占比过低；
- Java/Python 后端绝对主导；
- AI 仅套壳或岗位方向错位；
- 状态抑制；
- 用户覆盖与原因留痕。

#### P0-08 可解释单岗位 AI 分析

- 输入准备度；
- v0.7 正式上下文；
- 事实、规则、推断和建议分层；
- 支持证据、反证、缺口、风险与不确定性；
- 四档建议；
- HR 核验问题与沟通角度；
- Envelope 与 Payload 分离；
- stale 判定。

#### P0-09 0～8 条推荐批次与误区结果

- 用户从累计候选中选择 5～20 条；
- 默认只使用 current 成功分析；
- 0～8 条；
- 空推荐；
- 同公司相似岗位压缩；
- 处理状态抑制；
- 一个有证据门的主要误区或 `insufficient_evidence`。

#### P0-10 RadarAction

支持并留痕：

- 收藏 / 取消；
- 忽略 / 恢复；
- 重点 / 取消重点；
- 已投递待反馈 / 撤销；
- 规则覆盖 / 撤销；
- 动作绑定 candidate_version_id。

#### P0-11 RadarPromotion

- 关联或创建 Job；
- 高价值现实进展后关联或创建 Application；
- 必要时写入 FeedbackEvent；
- 晋升预览；
- 幂等；
- 从正式记录反向追踪来源、版本、分析、推荐和动作。

#### P0-12 AnalysisTask 与发布闭环

- 持久化任务；
- 幂等；
- 明确失败；
- 一次结构修复；
- 手动重试；
- 取消；
- 页面刷新恢复展示；
- 进程重启后恢复记录并处理遗留 running；
- 30 条真实岗位评测；
- migration、备份、恢复和真实截图验收。

原 v0.9 主动发现、保存搜索条件、后台来源运行、增量扫描、定时运行和持续简报能力已于 2026-08-27 退役，不再作为当前或后续版本承诺。其余新增能力必须重新经过独立范围确认。
- 字段级画像 diff；
- 反馈驱动职业画像进化闭环。

任何后续能力都必须复用 v0.8 的快照、来源记录、候选版本、规则、分析、推荐批次、动作与晋升关系，不得建立平行体系。

## 7. 核心用户故事

### US-01 当前页采集

用户在 BOSS 或其他岗位详情页点击“收进 OfferFlow”，看见预览和质量提示，修正后确认写入。

**验收：**

- 只读取当前页；
- BOSS 定向字段可用；
- 通用页面至少保存 URL、标题和可见文本；
- BOSS 定向抽取失败时可降级为通用可见文本；
- 不读取 Cookie、密码和其他标签页；
- 用户确认前不创建正式候选。

### US-02 采集预览与纠错

用户通过浏览器扩展采集当前页，进入统一预览、纠错并确认。

**验收：**

- 未识别字段保持未知；
- 可见文本为空或超限时明确报错；
- 用户确认前不创建正式候选；
- 不出现手工 JD 文本、链接组合或 JSON 对象/数组入口；
- 不出现独立批次管理主线。

### US-03 重复与变化

用户再次采集已见岗位时，系统说明它是未变化、实质变化还是疑似重复。

**验收：**

- 未变化不创建新 CandidateVersion、不重复分析；
- 实质变化创建新 CandidateVersion；
- 纯排版变化不触发；
- 疑似重复由用户裁决；
- 合并后不丢来源。

### US-04 数据质量与规则预检

用户在调用 AI 前即可看见缺失字段、硬约束、风险、偏好与状态抑制。

**验收：**

- 每个规则显示命中原文、分类、解释与严重程度；
- 用户可覆盖并填写原因；
- AI 失败时规则结果仍可用。

### US-05 可解释岗位分析

系统使用正式简历和岗位匹配画像解释“是否值得处理”，而不是复述 JD。

**验收：**

- Resume 与 JobMatchProfile 必须存在；
- 可选上下文缺失时正确降级；
- 非目标城市使用全局画像；
- 不虚构项目、年限、反馈和市场结论；
- 输出四档建议与证据。

### US-06 有限机会雷达

用户选择 5～20 条候选，系统收敛为 0～8 条优先机会。

**验收：**

- 不使用 stale 分析；
- 不凑数；
- 已处理岗位正确抑制；
- 空推荐有原因；
- 每条重点推荐说明“为什么现在处理”和“下一步核验什么”。

### US-07 误区诊断

用户看见这一批岗位中最可能的错误用力方向。

**验收：**

- 一批只有一个结果；
- 支持证据和反证同时展示；
- 证据不足时不强行形成正式误区；
- 诊断不修改正式画像。

### US-08 雷达动作

用户可以收藏、忽略、重点处理和标记已投递待反馈，并可撤销。

**验收：**

- 动作流水不可被覆盖；
- 当前处理状态由动作派生；
- 内容未变化时抑制重复打扰；
- 内容变化时可重新进入并展示变化。

### US-09 正式晋升

HR 回复、交换联系方式、安排笔试/面试、明确拒绝、用户主动重点跟进或明确要求时，系统提示晋升。

**验收：**

- 晋升前预览；
- 优先关联现有 Job/Application；
- 重复晋升幂等；
- 无回复不创建拒绝或能力反证；
- 撤销雷达动作不删除正式事实。

### US-10 任务失败与恢复

用户刷新页面或后端重启后，任务记录和结果不会凭空消失。

**验收：**

- 页面刷新恢复展示；
- 遗留 running 被识别为可重试失败；
- 重试复用固定输入；
- 不承诺中途续传模型请求；
- 旧成功结果保留；
- 相同输入不重复写入正式分析。

## 9. 核心产品流程

### 9.1 当前页采集

```text
用户打开岗位详情
→ 点击扩展
→ BOSS 定向解析或通用可见文本降级
→ 创建短期预览会话
→ 标准化与质量检查
→ 重复/变化预判
→ 用户纠错
→ 用户确认
→ 创建不可变 CaptureSnapshot
→ 关联 SourceRecord
→ 创建或关联 Candidate
→ 必要时创建新 CandidateVersion
```

### 9.2 采集会话预览

```text
扩展提交当前页 Capture Item
→ 打开统一预览会话
→ 校验与纠错
→ 用户确认
→ 生成 Snapshot、SourceRecord 与 CandidateVersion
```

### 9.3 单岗位分析

```text
CandidateVersion
→ 数据质量与输入准备度
→ 透明规则预检
→ 创建 AnalysisTask 与固定输入快照
→ 读取 v0.7 正式上下文
→ AI 返回纯 Payload
→ Zod 校验
→ 必要时一次结构修复
→ 服务端附加 Envelope
→ 保存不可变 AnalysisRecord
→ 展示四档建议与证据
```

### 9.4 推荐批次

```text
用户选择 5～20 个 CandidateVersion
→ 过滤未准备、硬阻断、stale 与状态抑制项
→ 必要时完成单岗位分析
→ 排序、同公司压缩与多样性约束
→ 选择 0～8 条
→ 生成批次证据摘要
→ 通过证据门生成一个误区或 insufficient_evidence
→ 保存不可变 RecommendationBatch
```

### 9.5 已投递待反馈

```text
用户在外部平台完成投递
→ 新增 RadarAction(marked_applied_pending)
→ metadata 记录 appliedAt / followUpDueAt / sourceSnapshotId
→ 推荐抑制与短期去重
→ 默认不创建 Application
→ 无回复不产生负向 FeedbackEvent 或 CandidateEvidence
```

### 9.6 正式晋升

```text
高价值现实进展或用户明确要求
→ 晋升预览
→ 重新读取现有 Job/Application
→ 在事务中创建或关联正式对象
→ 必要时写入 FeedbackEvent
→ 保存 RadarPromotion
→ 重复请求命中幂等
```

### 9.7 任务恢复

```text
任务已持久化
→ 页面刷新：继续读取状态
→ 进程重启：扫描非终态任务
→ 遗留 running：标记为可重试失败
→ 用户重试：复用固定输入从头执行
→ 唯一 input hash 防止重复正式结果
```

## 10. 透明规则与行动建议

### 10.1 规则分类

```ts
type RuleCategory =
  | 'hard_constraint'
  | 'risk'
  | 'preference'
  | 'state_suppression'
```

### 10.2 初始规则集合

#### 岗位性质

- 外包；
- 派遣；
- 驻场；
- 雇主不明；
- 短期合同；
- 纯维护；
- 纯切页面；
- 短期救火。

#### 技术结构

- 前端占比过低；
- Java/Python 后端绝对主导；
- AI 仅宣传词；
- 只要求训练、算法研究或模型底层；
- 缺少可迁移的前端、产品或应用工程空间。

#### 现实约束

- 明确不可接受城市；
- 通勤超过硬边界；
- 薪资低于城市底线；
- 工作制度冲突；
- 学历硬门槛；
- 经验硬门槛。

#### 状态抑制

- 相同岗位未变化；
- 已忽略且未变化；
- 已投递待反馈且未变化；
- 已晋升正式流程；
- 已明确拒绝且岗位未变化。

### 10.3 规则覆盖

用户覆盖必须记录：

- rule assessment；
- candidate_version_id；
- 原判断；
- 用户决议；
- 原因；
- 时间；
- 撤销关系。

一次候选版本上的覆盖不自动改写全局规则。

### 10.4 四档行动建议

| 建议 | 含义 | 默认行动 |
|---|---|---|
| 立即投递 | 当前策略内高匹配，主要风险可接受 | 优先准备并处理 |
| 重点冲刺 | 上限较高，但存在可解释缺口或竞争风险 | 投递并强化叙事/核验 |
| 观察验证 | 信息不足或关键条件未确认 | 暂缓，先核验 |
| 忽略 | 命中硬约束或价值明显不足 | 移出注意区，可恢复 |

## 11. 推荐与误区诊断规则

### 11.1 推荐资格

重点推荐必须满足：

- CandidateVersion 为当前 active version；
- 数据质量达到最低准备度；
- 未被未解除硬约束阻断；
- 分析成功且为 current；
- 推荐理由有证据；
- 未被当前动作状态抑制；
- 不是同一岗位重复项。

### 11.2 推荐数量

- 0～8 条；
- 默认目标 3～8 条；
- 同公司高度相似岗位默认一个代表；
- 没有合格岗位时输出空推荐原因；
- 推荐批次不可因模型失败自动降标准凑数。

### 11.3 误区证据门

形成正式误区至少需要：

- 当前批次有足够候选；
- 至少存在多个 current 成功分析；
- 主要模式可由多个候选或独立规则证据支持；
- 已检查反证；
- 结论能引用当前正式画像或策略中的明确字段。

不满足时输出：

```text
暂不形成正式误区诊断。
原因：当前批次样本或有效证据不足。
缺失证据：……
下一步：……
```

### 11.4 支持的初始误区类型

- 目标层级过高；
- 岗位方向与能力证据错位；
- 城市选择与当前策略错位；
- 薪资预期与岗位供给错位；
- 自身优势认知错误；
- 过度追逐 AI 全栈，忽视 AI 应用或高级前端基本盘；
- 重复处理已证明低价值的岗位族；
- 忽视已有高价值反馈；
- 证据不足。

## 12. 成功标准与发布质量门槛

### 12.1 用户成功

用户能够：

- 不截图地采集真实岗位；
- 识别同岗位未变化与实质变化；
- 在 AI 前看见透明规则；
- 获得有证据的单岗位四档建议；

- 在高价值进展后安全晋升；

### 12.2 发布硬门槛

- 至少 30 条真实或脱敏岗位评测；
- 至少一次 20 条以上真实 JD 的完整验收；

- 所有 must-detect 关键风险通过；
- 严重幻觉为 0；
- 重要结论 100% 有证据或明确不确定；
- 确定重复不得漏判；
- 疑似重复不得静默合并；
- 未变化不得重复分析；
- 实质变化必须创建新 CandidateVersion；
- 每批 0～8 条；

- 无回复污染为 0；
